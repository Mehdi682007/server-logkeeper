# Server Logkeeper

ابزار منودار مدیریت لاگ برای سرورهای **Ubuntu/Debian با systemd**؛ مناسب 3x-ui، لاگ‌های سیستم و Journal.

## نصب و اجرا

```bash
curl -fL https://raw.githubusercontent.com/Mehdi682007/server-logkeeper/main/logkeeper.sh -o logkeeper.sh &&
sudo bash logkeeper.sh
```

از منو گزینهٔ **2** را انتخاب کنید. سپس برای دفعات بعد:

```bash
sudo logkeeper
```

پیش‌نیازها در بیشتر سرورها نصب هستند. در صورت نیاز:

```bash
sudo apt-get update
sudo apt-get install -y curl logrotate python3 util-linux
```

فایل `.sh` با **Bash** اجرا می‌شود؛ از `sh logkeeper.sh` استفاده نکنید.

## منو

| گزینه | کارکرد |
|---|---|
| 1 | مصرف واقعی دیسک، زمان اجرای بعدی و نتیجهٔ اجراهای قبلی |
| 2 | نصب یا تغییر تنظیمات حجم، تعداد آرشیو و زمان‌بندی |
| 3 | پیش‌نمایش چرخش بدون حذف فایل |
| 4 | اجرای فوری چرخش با حفظ آرشیو فشرده |
| 5 | پاک‌سازی اضطراری با تأیید `YES` |
| 6 | نمایش گزارش اجراهای خودکار |
| 7 | حذف ابزار و بازگردانی تنظیمات قبل از نصب |
| 0 | خروج |

## تنظیمات

- آستانهٔ حجم هر لاگ: پیش‌فرض **100MB**، قابل تنظیم از 10 تا 10000.
- تعداد آرشیو برای **هر فایل**: پیش‌فرض **3**، قابل تنظیم از 1 تا 30.
- فاصلهٔ بررسی: **15، 30، 60، 180، 360، 720 یا 1440 دقیقه**؛ پیش‌فرض یک ساعت.
- بودجهٔ Journal: پیش‌فرض **200MB**، قابل تنظیم از 50 تا 10000.
- بررسی‌ها بر اساس ساعت سیستم انجام می‌شوند، نه مدت سپری‌شده از نصب. اجرای ازدست‌رفته در خاموشی با systemd پیگیری می‌شود.

آستانهٔ چرخش سقف لحظه‌ای نیست؛ در فاصلهٔ دو بررسی ممکن است لاگ بزرگ‌تر شود. حجم آرشیوهای قبلی هم به مصرف اضافه می‌شود. برای لاگ پرترافیک فاصلهٔ 15 دقیقه را انتخاب کنید. هیچ ابزار چرخشی پرنشدن دیسک را در برابر هر نرخ تولید لاگ تضمین نمی‌کند.

## چه فایل‌هایی مدیریت می‌شوند؟

فقط این فایل‌های مشخص در `/var/log/x-ui`:

```text
3xui.log
3xipl-ap.log
3xipl-ap.prev.log
3xipl.log
3xipl-banned.log
3xipl-banned.prev.log
```

همچنین برای سیاست موجود `/etc/logrotate.d/rsyslog` آستانهٔ حجم اضافه می‌شود؛ مسیرها، مجوزها و دستور بازکردن دوبارهٔ فایل توسط rsyslog حفظ می‌شوند. اگر rsyslog نصب نباشد این بخش نادیده گرفته می‌شود. زمان‌بندی عمومی logrotate نیز به فاصلهٔ انتخاب‌شده تغییر می‌کند؛ سیاست زمانی سایر بسته‌ها حفظ می‌شود.

Journal محدودیت دائمی دریافت می‌کند. اعمال این محدودیت نیازمند بازراه‌اندازی `systemd-journald` است؛ پنل، Xray و سرویس‌های شبکه ری‌استارت نمی‌شوند. کاهش سقف ممکن است بلافاصله لاگ‌های قدیمی Journal را حذف کند.

### چرخش معمول در برابر پاک‌سازی اضطراری

**گزینهٔ 4:** فقط فایل‌هایی که مطابق سیاست نیاز به چرخش دارند آرشیو می‌شوند. دستور بدون `--force` اجرا می‌شود؛ فایل کوچک الزاما تغییر نمی‌کند.

**گزینهٔ 5:** محتویات شش فایل مشخص را خالی می‌کند و از آخرین 1MB هر فایل یک نمونهٔ فشرده با پسوند `.cleanup-tail.gz` نگه می‌دارد. نمونهٔ قبلی همان فایل جایگزین می‌شود. کش دانلود APT و Journal قدیمی هم پاک می‌شوند. آرشیوهای معمول، دیتابیس، کاربران، تنظیمات پنل، گواهی‌ها و فایل‌های دیگر حذف نمی‌شوند. این گزینه نیازمند تأیید صریح است و پاک‌سازی خودکار به آن وابسته نیست.

لاگ‌های 3xipl ممکن است برای عیب‌یابی محدودیت IP یا ابزارهای خوانندهٔ لاگ استفاده شوند؛ کم‌کردن نگهداری، سابقهٔ در دسترس آن‌ها را هم کم می‌کند. در پاک‌سازی اضطراری سوابق حذف‌شده قابل‌بازگشت نیستند.

## نکات فنی و محدودیت‌ها

- چرخش x-ui با `copytruncate` است؛ به ری‌استارت پنل نیاز ندارد، ولی در لحظهٔ کپی/خالی‌کردن احتمال از دست‌رفتن تعداد کمی خط وجود دارد.
- بعضی نسخه‌های پنل پس از truncate از موقعیت قبلی فایل می‌نویسند و فایل sparse ایجاد می‌کنند. اندازهٔ ظاهری در `ls -lh` می‌تواند بزرگ باشد؛ `du -h` و `df -h` مصرف واقعی را نشان می‌دهند. این رفتار می‌تواند باعث چرخش‌های بیشتر و زمان پردازش طولانی‌تر شود؛ ابزار رفتار داخلی پنل را تغییر نمی‌دهد.
- اجرای اولیه روی چند گیگابایت لاگ ممکن است چند دقیقه طول بکشد و برای ساخت آرشیو موقت به فضای آزاد نیاز داشته باشد. اگر دیسک کاملاً پر است، ابتدا گزینهٔ 5 را اجرا کنید.
- سه آرشیو **برای هر لاگ** نگهداری می‌شود؛ نه سه آرشیو در کل سرور.
- سیاست‌های سفارشی پیچیدهٔ rsyslog و نصب‌های Docker پشتیبانی نمی‌شوند. از دوباره‌تعریف‌شدن مسیر x-ui در `/etc/logrotate.d` جلوگیری می‌شود.
- ابزار فقط لاگ‌های مسیر استاندارد فوق را مدیریت می‌کند؛ لاگ Docker، بکاپ‌ها و فایل‌های برنامه‌های دیگر تحت پوشش نیستند.
- ابزار اطلاعاتی ارسال نمی‌کند، به SSH متصل نمی‌شود و هیچ رمز یا نشانی سروری داخل کد ندارد.

## مسیرهای نصب و بازگردانی

```text
/usr/local/sbin/logkeeper
/etc/server-logkeeper.conf
/var/lib/server-logkeeper/backup/
/etc/logrotate-x-ui.conf
/etc/systemd/system/x-ui-logrotate.service
/etc/systemd/system/x-ui-logrotate.timer
/etc/systemd/system/logrotate.timer.d/90-hourly.conf
/etc/systemd/journald.conf.d/90-log-retention.conf
```

از تنظیمات اولیه فقط یک‌بار نسخهٔ پشتیبان گرفته می‌شود؛ تغییر تنظیمات منو آن را بازنویسی نمی‌کند. گزینهٔ حذف، همان وضعیت **قبل از اولین نصب** را برمی‌گرداند؛ اگر پس از نصب دستی این فایل‌ها را ویرایش کرده‌اید، پیش از حذف از ویرایش‌ها نسخه بردارید. فایل‌های لاگ باقی می‌مانند و نسخهٔ پشتیبان با نام `server-logkeeper.uninstalled.*` حفظ می‌شود.

این ابزار با نام فایل‌ها و timerهای نسخهٔ دستی قبلی سازگار است؛ اگر آن نسخه از قبل نصب باشد، هنگام حذف ابزار، همان تنظیمات قبلی بازگردانده می‌شوند.

## خط فرمان

```bash
sudo logkeeper --status
sudo logkeeper --install
sudo logkeeper --preview
sudo logkeeper --rotate
sudo logkeeper --clean
sudo logkeeper --uninstall
```

## آزمون

```bash
bash -n logkeeper.sh
shellcheck logkeeper.sh
python3 tests/test_logkeeper.py
```

تست‌های خودکار با فایل‌های موقت و سرویس‌های شبیه‌سازی‌شده اجرا می‌شوند و تنظیمات میزبان را تغییر نمی‌دهند. اجرای واقعی systemd روی سرور مقصد از طریق گزینهٔ وضعیت و گزارش قابل بررسی است.
